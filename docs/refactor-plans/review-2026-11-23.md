# Deferred from the 2026-11-23 review

## Share item lookup across buy and craft forms

**Why**  
The buy and craft pickers search different name sources. Typed input uses a third lookup path, so a name can resolve to a different item or game than the picker suggests.

**Where**  
`src/app/Livewire/Trades.php` (`suggestions`, `craftItemPicker`), `src/app/Services/TradesService.php` (`resolveItem`), `src/app/Support/ItemName.php` and the Buy and Record a craft forms in `src/resources/views/livewire/trades.blade.php`.

**Proposed approach**  
Define which names apply in each game, how personal names override the catalog, and when a duplicate name requires an ID. Reuse those rules for suggestions and typed input. Share picker markup where the controls have the same behavior, with stock and vendor prices supplied by the craft form.

**Risks and open questions**  
Decide whether to keep accepting old catalog aliases after a personal name is learned. Preserve direct ID entry and verify that older saved items still display and edit correctly. Establish which callers still need global catalog lookup before narrowing any API.

**Suggested scope**  
Cover manual buy, recipe and craft entry and their shared name rules. Leave ingest, CSV and pasted-trade matching outside this refactor.

## Preserve ingredient stock for later recorded crafts

**Why**  
A backdated craft can consume ingredients already used by a later recorded craft. The replay then consumes whatever remains for the later craft and still records its full output, understating its cost.

**Where**  
`src/app/Services/TradesService.php` (`addCraft`), `src/app/Services/PositionsService.php` (`stockForCraft`, `heldForCraft`), and `src/app/Services/LedgerService.php` (`buildFromSales`, `replay`).

**Proposed approach**  
Check a proposed craft against later recorded ingredient uses in the same chronological replay, and reject entries that create new shortages in existing crafts. Batch affected ingredients in one validation pass. Serialize overlapping craft writes so validation and persistence agree.

**Risks and open questions**  
Decide how to handle existing shortages and whether to report the first affected craft or every affected craft. Keep the ledger's event order for same-second buys, craft uses, outputs, sales and corrections.

**Suggested scope**  
Cover craft insertion and later craft ingredient shortages. Preserve the behavior that permits backdating ahead of a later sale, which the ledger can classify as a sale of untracked stock.
